# Trading Tool — Project Context

Personal decumulation trading tool for a German tax resident (Berlin), tracking real holdings on Trade Republic/Scalable Capital via a local FastAPI + vanilla JS app. Not a product — one user, real money, local-only. Full background: `~/Downloads/trading-tool-project-brief.md`.

## Running it

The web server runs as a **launchd agent** (`~/Library/LaunchAgents/com.tradingtool.webserver.plist`, `RunAtLoad` + `KeepAlive`), so it auto-starts at login and restarts within ~10s if it dies. `http://127.0.0.1:8000` should always be up — no manual start needed. This is the fix for the recurring "can't connect" problem: previously the server only ran when a terminal was open, so it died on logout/sleep/reboot.

Everyday commands:

```bash
# Is it running? (a PID in the first column = live)
launchctl list | grep webserver

# Reload after editing code (launchd runs WITHOUT --reload, so changes need a manual restart)
launchctl kickstart -k gui/$(id -u)/com.tradingtool.webserver

# Stop auto-start entirely / re-enable
launchctl unload ~/Library/LaunchAgents/com.tradingtool.webserver.plist
launchctl load   ~/Library/LaunchAgents/com.tradingtool.webserver.plist
```

Server logs go to `webserver.log`. If launchd shows a stale non-zero exit code but there's a live PID and `curl http://127.0.0.1:8000/` returns 200, it's fine — the code is just the *last* exit, not current state.

Manual run (dev only, e.g. to see live-reload on edits — don't run alongside the launchd one or you'll get an "address already in use" port clash):

```bash
./venv/bin/uvicorn main:app --reload --port 8000
```

Python 3.9 venv — **no `X | Y` union type syntax** (needs `Optional[X]` from `typing` instead, or it breaks at import).

## Architecture

- `main.py` — FastAPI app, all `/api/*` routes, holdings data model (`data/holdings.json`). **Holdings are multi-lot**: each has a `lots` list `{shares, cost_basis, purchase_date}`; `recompute_aggregates()` derives the position-level `shares`/`cost_basis` (weighted avg)/`purchase_date` (earliest) that the rest of the code + UI read, so lots are the source of truth. **Sells are FIFO** (oldest lots first → realized gain matches the broker, records a `lots_sold` breakdown). Lot CRUD: `POST /api/holdings/{id}/lots`, `PUT/DELETE .../lots/{index}`. The plain Edit form forwards shares/cost/date onto the single lot for one-lot holdings; multi-lot edits its shares/cost only via the Lots modal. Position-level things (stop/reference_high/exit_plan/current_price) stay singular. Selling a holding (partial or full) via `POST /api/holdings/{id}/sell` logs an entry to `data/sales_history.json` (`GET`/`DELETE /api/sales-history*`) rather than a plain delete — there is no bare delete-holding endpoint anymore.
- `prices.py` — Finnhub (quotes, analyst consensus, earnings history/calendar, insider transactions, company news) + Frankfurter (USD→EUR rate). No key needed for Frankfurter; `FINNHUB_API_KEY` in `.env` for the rest.
- `ls_tc.py` — **the preferred price source for any holding with an ISIN set.** Fetches the live EUR mid-price directly from Lang & Schwarz (`ls-tc.de`) — the actual venue Trade Republic trades US-stock orders against — instead of the Finnhub-based anchor/roll-forward approximation in `apply_quote`. Public site, no login, `robots.txt` fully permissive, ToS explicitly allows reproduction for personal/private/non-commercial use — the fit for this tool; deliberately scoped to holdings only (a small, user-curated set), not the Opportunities/Opportunities B screening lists, since there's no reliable free ticker→ISIN source at the hundreds-of-tickers scale those cover. Uses ls-tc.de's own internal JSON endpoints (`/_rpc/json/.lstc/instrument/search/main` to resolve an ISIN to their internal `instrumentId`, cached in `data/ls_tc_cache.json` since that mapping never changes; `/_rpc/json/instrument/chart/dataForInstrument` for the live price) — not HTML scraping. Their search only reliably matches by ISIN/WKN, not ticker or company name (tested: "AMD" matched "AMDOCS", the full company name matched nothing) — ISIN must come from the user (Trade Republic shows it per-instrument). `main.py`'s `apply_ls_tc_price()` is tried first on every refresh (single and bulk); on success it overwrites `current_price` and `day_change_pct` directly (both from the same L&S reference point) and clears any leftover anchor fields — no anchor bookkeeping needed since it's a real price, not an approximation to correct. Falls back silently to the existing Finnhub path if there's no ISIN or the L&S fetch fails (e.g. outside L&S's ~07:30–23:00 CET trading hours). Live-validated across all 10 real holdings (2026-08-13): most landed within ~0.2% of the TR app, aggregate portfolio total within ~0.25% — a large improvement over the Finnhub approximation. Also resolved the long-standing LNVGY problem (see PRICE_MISMATCH_FACTOR note below): its real ISIN (the underlying HK-listed Lenovo Group ordinary, not the US ADR ticker) is directly priceable via L&S, so `manual_price` was turned off for it once the ISIN was added. **L&S's `day_change_pct` can be noticeably off even when the price itself is right** — real example (WDC, 2026-08-27): live price converted to USD matched Yahoo almost exactly (\$453.78 vs \$453.81), but L&S's *previous-close* reference was ~\$7.6 (~1.6%) higher than Yahoo's actual previous close, making the day's decline read as -4.76% on L&S vs -3.21% on Yahoo — L&S's previous-close reference appears to occasionally lag (still anchored to an older close), not the current price. If a day-change % ever looks unusually large next to another source, suspect this before assuming a real move or a portfolio bug.
- `consensus_store.py` — the **only** place that should call `prices.fetch_analyst_consensus()`. Holdings, Opportunities (Zacks), Watchlist, and Analyze/Compare all show the same Zacks-style 1–5 analyst consensus average for a ticker, and used to each fetch it independently (four separate live calls, four separate storage spots) — so the same ticker could show a different number on different screens depending on which happened to be refreshed most recently. `consensus_store.refresh(ticker)` is the one fetch+write path (every refresh trigger, wherever it lives, calls this); `consensus_store.overlay_consensus(ticker)` is called by the `GET /api/holdings`, `/api/zacks`, `/api/watchlist` handlers to overlay the shared cached value at read time, so a refresh from any one surface shows up everywhere immediately — not just wherever it was clicked. `data/consensus_cache.json`. Adding a new consensus display anywhere: read through this, don't add a fifth independent fetch.
- `alpha_vantage.py` — news sentiment + daily price history (`ALPHA_VANTAGE_API_KEY` in `.env`, free tier 25 req/day **shared across both**). Both are cached per-ticker-per-day (`data/price_history_cache.json`, `data/news_sentiment_cache.json`) since Analyze can be clicked on the same ticker more than once a day and this quota is easy to blow through — a verification loop across 11 holdings did exactly that on 2026-08-17, which is what prompted caching sentiment too (it wasn't before, unlike price history). Any new Alpha Vantage-backed feature should think about this shared budget, and any live-testing loop across multiple tickers should account for its cost before running.
- `risk.py` — per-ticker **historical volatility**: annualized std-dev of daily returns from the last ~90 trading days (via `alpha_vantage.fetch_daily_prices`, so free if that ticker's chart was already viewed today), bucketed Low/Moderate/High/Very high. Purely backward-looking and labeled as such — deliberately not fed to the synthesis LLM (kept out of `SYSTEM_PROMPT`'s scope), just a standalone badge in the Analyze popup alongside Opp B score/sector context. See `docs/plans/roadmap.md` for the risk-assessment discussion this came out of.
- `momentum.py` — **momentum-burst signals**, descriptive only, same spirit and same `SYSTEM_PROMPT` exclusion as `risk.py` (words like "breakout" read as a recommendation once an LLM narrates them; a badge showing "+22% over 5 days, closed mid-range" leaves the reading to the user). Thresholds come from Pradeep Bonde's "momentum burst" rules; deliberately **no A/B/C rating, no score, no entry/stop/size** — those are the parts of that methodology that cross into advice. `from_finnhub(shape, metrics)` runs off a live `/quote` plus `stock/metric`, both already fetched wherever it's used, and powers the **Today's momentum** badge in Analyze. An earlier second tier read Alpha Vantage daily bars (adding volume vs. the 50-day average and range expansion) but was **deleted 2026-09-05**: those bars lag a day, so the badge kept describing yesterday while labelled today — it read "quiet" on STRL at a moment the stock was up 5%. One live read is worth more than two extra fields that are silently stale. States: `burst` / `extended` / `sharp drop` / `quiet`, plus a separate `trend` (`uptrend`/`downtrend`/`mixed`) from the 13-week return and distance from the 52-week high. **The trend field is the point**: Bonde's setups assume a stock already trending up, so a burst inside a decline is a bounce, not a breakout — real case (STRL, 2026-09-04) rose 5% while sitting 52% below its June high. Two rules from the original method were deliberately dropped after live testing: the **dollar breakout** (close−open ≥ $0.90) fires trivially on high-priced stocks — on AMD ($473) it flagged a day the stock closed *down* 0.2% — and `pct_from_52w_high()` (shared with `fundamentals.py`) rejects Finnhub 52-week ranges that describe a different listing than its own `/quote` (TSM: `/quote` returns the US ADR ~$427, the metric block returns the Taiwan listing's 2535/1145 TWD range, which rendered as "-83% from its 52-week high").
- `fundamentals.py` — **price vs. profits**, the lens the rest of the tool structurally lacks. Zacks rank, Opportunities B, momentum and sentiment are all trend-following ("is this working now"), so they read bearish on any recovery thesis by construction — which tells the user nothing. This asks instead whether the *price* fell while the *business* kept growing (the recovery setup) or both deteriorated (the value-trap shape). Free: runs off `prices.fetch_metrics()` + `fetch_earnings_history()`, both already fetched for Analyze. Same `SYSTEM_PROMPT` exclusion and badge-not-prose treatment as `risk.py`/`momentum.py`. **`multiple_change_pct` is derived, not measured** — `(1 + price_return) / (1 + eps_growth) - 1` recovers how the market's per-unit-of-profit valuation moved without any historical-P/E data, which no free source provides; returns `None` once profits cross zero, since profit→loss isn't a valuation change. Must use the **12-month** price window because Finnhub's growth figures are TTM year-over-year — but that window is blind on its own: live-tested across STRL/AMD/NEM/FN (2026-09-05) *every* ticker came out `in_line`, STRL included, because its 52% fall since June sits inside a 12-month period that was still net positive. So `price_3m_pct` and `pct_from_52w_high` (reusing `momentum.pct_from_52w_high()`, inheriting its TSM currency-mismatch guard) are reported alongside, and **the pairing is what carries the meaning**: a flat valuation with a deep drawdown says the earlier peak was the anomaly (STRL), while a fallen valuation says investors pay less for the same profit than a year ago while profits grew (FN: −23%, profit +42%, −46% from high — the clearest divergence in the set). The headline can't come from the sign-only quadrant either: FN's price +9% vs. profit +42% is technically "both positive" while the valuation fell 23%, so `fundamentalsLabel()` in `app.js` lets the valuation change decide between "Profits grew faster than the price" and "Price rose faster than profits" when both rise. `eps_base_distorted` guards a live edge case: above +200% year-over-year profit growth the figure is a rebound from a near-zero base rather than expansion and the derived valuation change is nonsense — GEV showed +744%, which rendered as "investors pay 81% less for the same profit" before the guard. **Copy is deliberately plain and short** (the user reads this to understand, without a finance background): "profits" not "earnings", "investors now pay 23% less for the same profit" not "the market's valuation of each dollar of earnings fell 23%". Sales growth, the P/E figure and the beat record were **removed** rather than reworded — the beat record already appears in the signals table right above it, and the rest crowded out the single comparison the badge exists to make. Target ~70 words. **Sentence order is load-bearing**: the 3-month price move goes *last*, after the valuation conclusion. Sitting between the yearly price/profit pair and the "so investors now pay X% more" that follows from it, the quarter read as the conclusion's premise — a false causal link the user spotted across several tickers. It also states why it has no profit counterpart (Finnhub's growth figures are trailing-twelve-month), since a lone price number next to a paired one looks like something is missing. **The closing "it can't say whether a fall is over" only appears when there is a fall** — it ran unconditionally at first and read as a non-sequitur on a stock that had risen (caught on NEM, up 74% over the year). Each situation gets its own closing reading rather than only the falling one: a risen stock is told how much of the gain came from the business earning more versus the market paying more, since the second half can reverse without the company doing anything wrong — without it the badge gave a number and explained nothing for anything not in a drawdown.
- **Risk preview on Watch List items** (2026-09-05) — a per-row **Risk** button opens a modal (`openRiskModal()`/`renderRiskPreview()` in `app.js`, frontend-only since the maths is trivial and both inputs are already loaded): enter an amount and a stop distance, and it shows the share count, the position as a share of the *enlarged* portfolio, the stop price, and what a stop-out would cost in euros and as a portfolio percentage. This is the genuinely borrowable half of the `breakout-trade-planner` skill reviewed on 2026-09-04 — arithmetic about a hypothetical. **It deliberately does not suggest an amount**: the sizing multipliers and share counts in that skill are the part that crosses into advice, and the amount is the user's input here, never an output. The stop defaults to 10% because that is what 8 of her 10 holdings use (MU and NBIS are ~22%), and the hint says so — describing her own practice, not recommending a level. Always ends by noting a stop doesn't guarantee the exit price, since a gap opens below it. Extended the same day into a **pre-buy checklist** (roadmap item 7): the modal is now "{TICKER} — before you buy" with three sections. *What it would put at stake* is the risk arithmetic above. *What the tool already knows* answers what it can rather than asking — and **every line must be about that stock**. The first version opened with the portfolio's largest bloc and the market's breadth figure, which were word-for-word identical on every ticker: they read as facts about the stock while being facts about the portfolio, and the user rightly called them irrelevant. Both were removed, since the **Check** button already reports each stock-specifically (naming the bloc it would join, and giving the breadth share as the denominator for where this one sits). What remains is per-stock: a 3-month drawdown ≥20%, the #tag group this ticker belongs to and whether that group is working or unwinding, and how far the price has moved since it was added. **Deliberately no pass/fail or score**: a tick would read as approval, and this is context, not a verdict. *What only you can answer* is three fixed questions — the thesis and its falsifier, what is being given up to fund it, and how it would feel to hold through a drawdown — saved to the watch item (`why`/`tradeoff`/`drawdown`) and folded into the holding's `why` on promotion. The static/adaptive split decided 2026-09-04 holds: these three don't change per stock, which is why they belong in the interface; the adaptive questions ("this is a recovery thesis, so ask about the multiple") can't be pre-written and stay a conversation.
- **Thesis capture on holdings** (2026-09-05) **Buying a watched ticker carries its reasoning across**: a **Bought** button on a Watch List row (`promoteWatchItem()`) switches to My Stocks, pre-fills the ticker and today's date, and shows a banner naming what will happen. On a successful add, `addHolding()` copies the watch item's `why`/`source_url` onto the new holding and deletes the Watch List entry. The two lists had no connection at all before this, so buying meant retyping into a separate form and abandoning the note exactly when it started mattering. Guarded by ticker match — editing the ticker field before submitting silently cancels the promotion rather than attaching the wrong thesis — and there is a visible cancel link. — a per-row **Why** button opens a modal (`openThesisModal()` in `app.js`, `PUT /api/holdings/{id}/thesis`) holding a free-text `why` and an optional `source_url`, validated by the same `clean_source_url()` as the watchlist. Deliberately a modal and not a column: the holdings table is already 13 columns wide, and the reasoning is a paragraph, not a cell. The button reads "Why ✓" once something is written. **One textarea, not separate why/falsifier fields** — the same call as the Watch List, where a structured tag/why split was built and rolled back the same day; the placeholder prompts for both instead ("Why you own it — and what would tell you you're wrong"). This is distinct from `exit_plan`, which says what to do at the stop; this says why the position is owned at all. It exists because the Watch List had thesis capture and holdings — where the real money is — did not, the same gap `concentration.py` closed for correlation.
- **Theme lifecycle on your own #tags** (2026-09-05, `renderThemeStages()` in `app.js`) — the free answer to roadmap item 8. The `theme-detector` skill stages 14 market-wide themes but needs FINVIZ Elite (€35/mo) and scrapes in its free mode; this stages the groups the user actually formed, from two trailing returns already stored on each watch item. `fetch_watch_data()` now also keeps `move_12m` and `off_high` from the `stock/metric` call it already makes, so staging costs **no extra requests**. Four plain states from the sign of the 12-month and 3-month returns: *still working* (both up), **was strong, now unwinding** (year up, quarter down), *falling for a year, rising lately*, and *not working*. Groups of one are skipped — that's a stock, not a theme. First reading: `#ai` 5 names +51.4% over the year but −23.4% over 3 months and 36% off their highs (unwinding), against `#gold` 3 names +51.1% and +17.5% (still working) — the distinction the paid skill's five-stage label was wanted for, from data already in hand.
- **`watchlist_history.json` / `record_watchlist_snapshot()`** (2026-09-05) — one price point per watch-list ticker per day, written on every refresh-all, mirroring `record_holdings_snapshot()`. Exists because **Finnhub's free tier serves no price history at all** — `stock/candle` and `stock/tick` both 403 (live-tested 2026-09-05), and `stock/metric` gives trailing returns but no series — so comparing a candidate against holdings had to spend from Alpha Vantage's 25/day cap. Every refresh already fetches a price, so recording it builds the same series for nothing: `concentration.compare_candidate()` prefers this recorded series and falls back to Alpha Vantage only until enough days accumulate (`source` in the payload says which was used, and the UI prints it). The general lesson, which the user reached first: for the small curated sets this tool cares about, recording our own history beats paying a per-request budget for someone else's.
- `breadth.py` — **how much of the market is participating**, `GET /api/breadth`, panel in My Stocks. Every other signal here looks at one company; this looks at the market underneath them — the share of US stocks above their own 200-day and 50-day averages. A rise carried by most stocks is a different environment from one carried by a few, and breakout-style setups fail disproportionately in the second, which is context the momentum badge cannot supply. Source: TraderMonty's published CSV on GitHub Pages — no key, no login, a dataset deliberately published for public use, so it clears the no-ToS-violating-scraping rule (live-verified 2026-09-05: HTTP 200, ~450 KB, ~10 years of daily rows). Cached once a day in `data/breadth_cache.json`; a failed fetch falls back to the cached rows rather than erroring, and the UI always prints the `as_of` date so a frozen third-party feed is visible rather than silent. It is one person's dataset and could stop updating — that is the main risk, and why the date is shown. First reading (2026-09-03): 68.7% above the 200-day but only 51.1% above the 50-day, the latter down 13.8 points in a month — a market narrowing under the surface while the index held up. **The copy explains the measure before using it** — "a stock trading above its own average price of the last 50 days has been rising lately" — because "51% above their 50-day average" is meaningless without knowing what that average is or why being above it matters. It also reports the **prior level** ("was 64.9% a month ago") rather than a change: 64.9 → 51.1 is 13.8 percentage *points*, and the first version wrote "down 13.8%", which is a different and wrong number. `stock_position(ticker)` (`GET /api/breadth/position/{ticker}`) places one stock inside that market figure using the identical measure — "it is one of the 48.9% that are not rising, 7.2% below its own 50-day average". Without it the breadth number is trivia: the user's question was "where does *this* stock fall in that?", and answering it is what makes the market statistic a place to stand. Only the 50-day is computed — Alpha Vantage's free tier returns ~100 trading days, so a 200-day average is out of reach (`outputsize=full` is premium). Surfaced by the same **Check** button as the overlap comparison in the pre-buy modal: both read through `alpha_vantage`'s per-ticker-per-day cache, so asking for both costs one call rather than two.
- `concentration.py` — **which holdings move together**, `GET /api/concentration`, panel in My Stocks. The % Portfolio column shows how *big* each position is; it cannot show that several positions are one bet. Free: `data/holdings_history.json` already records each holding's value daily, and while the share count is unchanged a change in value *is* a change in price, so no price history is fetched. **That assumption is the trap, and `_changed_shares()` guards it** — a sale or a new lot inside the window moves the value without the price moving, which reads as a huge fake one-day return. This is not theoretical: an unguarded first pass reported FIX·LNVGY at +0.78 as a possible data-centre link, when in fact both had lots bought on 2026-08-18 and the correlation was pure artifact. Sales are keyed on `sell_datetime` (not `sell_date` — the first version silently never matched). Grouping is connected components over pairs above `CORRELATION_THRESHOLD` 0.5, chosen because n=21 daily returns puts the 5% significance level near r=0.43; each group also reports its `min_correlation` so the UI can say when a bloc was chained through a middle holding rather than every member agreeing. First real result (2026-09-05): AMD/MU/NBIS/WDC move as one bloc worth 37% of the portfolio, while **PLTR — the largest single position at 22% — correlates *negatively* with most of it**, so the intuitive "most of this is AI" read is materially wrong about the risk. Descriptive only: it names the blocs and their weight, never what to do about them. `compare_candidate()` (`GET /api/concentration/compare/{ticker}`, a button in the pre-buy modal) answers the same question for a ticker **not** held: `analyze()` structurally can't, since holdings_history records only holdings, so this fetches the candidate's daily closes from Alpha Vantage and lines them up against the recorded values. **Sector is deliberately not used for this** — GICS files the user's own AI bloc under two sectors and leaves one member unclassified, so it answers a different question than "do these move together". Behind a button because it spends from the 25/day Alpha Vantage budget the first time a ticker is checked each day. Two caveats surfaced in the UI: holdings are valued in EUR while the candidate's closes are USD, so a little currency movement leaks in, and only dates present in both series are used (GEV overlapped on 14 of 21 days). Live result: GEV correlates 0.49/0.46/0.39 with NVDA/MU/NBIS — leaning towards the bloc without clearing the 0.5 bar, reported as "leans towards your existing holdings without clearly joining them" rather than forced into a yes or no. Also reports **down-day behaviour** (`_down_day_behaviour()`): correlation measured across calm days answers the wrong question, since holdings that trade independently day to day often fall together in a shock — exactly when the diversification was meant to help. So it shows each holding's average return on the portfolio's worst 25% of days. First result (2026-09-05, 5 worst days, portfolio −2.3%): NBIS −6.3% and WDC −4.2% amplified, while PLTR came in at −0.2% and fell on only 3 of 5 — its independence holds under stress, not just on average. **Correlations are market-adjusted** (`market_adjusted` in the payload): the S&P level shipped in the same breadth CSV is subtracted from every series first, because raw correlation over a few weeks is inflated by most stocks falling on the days the market falls — a candidate can score ~0.5 against a bloc merely for being a normal risky US stock. The user spotted this from the symptom ("I check different stocks and get the same line"). It changes real answers: ONTO went from joining the bloc (AMD +0.58) to not (+0.32), while RDDT's link survived (NBIS +0.53 both ways) and NEM fell from +0.26 to +0.08. Two gotchas found while wiring it: the cached breadth rows predate the `spx` field so a `force=True` refetch is needed once, and requiring *every* shared date to exist in the market series silently disabled the adjustment, since that feed lags a day or two — the overlap is intersected instead.
- **Analyze popup ordering and weight** (2026-09-05) — `renderSignals()` orders by how much each piece changes the reading, not by build order: *Price vs. profits* first, then the tensions, then sector / Opportunities B / volatility / today's move as reference, then the table and the LLM prose. Before this everything carried equal weight, and the user's complaint was exact — the one paragraph that actually explained STRL sat fifth, under three lesser badges, while *today's* move got a full explanatory paragraph she had already twice called low-value. **Today's move is now a single line** (`renderMomentum` returns a `<p class="subtitle">`, not a badge). The **burst-inside-a-downtrend contradiction was deleted** from `derive_signals()` — that line already says it, and repeating it at paragraph length padded a box whose whole value is that every entry is worth stopping for. `renderSectorContext()` now takes the stock's own 3-month move and **states the comparison instead of posing it**: it used to end "is the stock swimming with or against its sector's tide?" while holding both numbers needed to answer (STRL −51.9% against a sector at −0.7% → company-specific, not sector weather). Same fault, same fix, as the pre-buy bloc line.
- `synthesis.py` — assembles Zacks + Finnhub + Alpha Vantage + Opportunities B data for one ticker and calls Claude (`ANTHROPIC_API_KEY`) for a prose synthesis. See `docs/plans/synthesized-stock-analysis.md` for the full design and the "no directive conclusion" prompt boundary — read that before touching `SYSTEM_PROMPT`. The prose is deliberately compact: `SYSTEM_PROMPT` targets ~180-250 words in 3-4 theme-grouped paragraphs (not one paragraph per data category), each with a bold lead-in — a first version ran ~900 words/5 paragraphs and Liraz found herself skimming instead of reading (2026-08-13). `derive_signals()` is the deterministic (non-LLM) contradiction-flagging layer — besides the original within-Zacks checks (rank vs. VGM, rank vs. price, rank vs. earnings surprise) — the earnings-surprise one only counts a miss in the **last two quarters** (`RECENT_QUARTERS`, and Finnhub returns them newest-first). It originally scanned all four and called whatever it found "a recent stumble": on MPC that flagged a miss from 2025-09-30, the *oldest* of the four, which had been followed by three straight beats — an improving record reported as a warning, and the wording claimed "recent" about something a year old, it also flags **Zacks Rank vs. Opportunities B** divergence both directions (Rank bullish but Opp B score below the current shortlist cutoff, or vice versa — e.g. AEHR/INOD, 2026-08-13), prefixed `"Conflicting signal:"`/`"Mixed signal:"` so the tension reads as explicitly not-reassuring rather than needing the user to infer it. Only fires when there's an actual Opp B score to compare (no analyst coverage → silently skipped, not treated as tension) and notes when the ticker is outside the S&P 500 universe Opp B actually screens (`opportunities_b.in_universe()`), since "never scanned" and "scanned and scored low" are different situations worth distinguishing. Two further checks came out of a real case (STRL, 2026-09-04): a **ratings vs. sustained decline** flag, because the existing rank-vs-price check only looks back **4 weeks** and STRL's 52% fall was spread over three months, so nothing saw it (fires on a bullish rank *or* a consensus ≤ 2.0 against a 13-week return ≤ -20%, and is suppressed when the 4-week check already fired, to avoid two bullets saying the same thing); and a **burst-inside-a-downtrend** flag, reading `momentum.py`'s state/trend. `derive_signals(data, momentum_data)` therefore takes the momentum result as a second argument — `synthesize()` computes it once and passes it to both the signals and the response. It also computes `_earnings_risk()` (2026-08-17): a **forward-looking** flag (not a recap of a past reaction, which Liraz explicitly didn't want) — triggers when a holding is within 21 days of its next earnings date, up ≥15% over 4 weeks, and news sentiment reads Bullish (≥0.35, Alpha Vantage's own threshold) — "expectations running hot ahead of earnings," motivated by MU/AMD beating big and dropping anyway. No new API calls, reuses data already fetched for Analyze. The planned follow-up (a per-ticker beat-to-price track record across past quarters) was dropped (2026-08-18) after two live-tested dead ends — Finnhub's `calendar/earnings` can't get historical dates per symbol (see the hard-rule note below), and the Alpha Vantage/Stooq pivot that would've supplied years of price history for the reaction check also failed (AV's `outputsize=full` is premium-only; Stooq disallows automated access via `robots.txt` and now sits behind an active bot challenge) — full reasoning in `docs/plans/roadmap.md`.
- `opportunities_b.py` — a second, deliberately-short opportunities source, methodologically different from Zacks: an analyst-conviction shortlist over the **S&P 500** (universe bundled in `data/sp500.json`, since Finnhub's constituent endpoint is paywalled). Two-stage funnel (consensus over 500 → top 40 → add earnings-beats → top ~20), composite = 0.45 conviction + 0.45 beats + 0.10 opinion-drift (drift read free from the 4-month history Finnhub returns in the recommendation call — no snapshot pipeline). Output `data/opportunities_b.json`; `build()` takes `universe_limit` for quick tests. Descriptive/sorted, never a pick. Refresh is a ~10-min synchronous batch (`POST /api/opportunities-b/refresh`), like the Zacks consensus refresh. `score_ticker()` computes the same composite on demand for *any* ticker regardless of S&P 500 membership or shortlist placement (used by `synthesis.py`); `in_universe()` and `shortlist_cutoff()` (lowest composite currently making the top-20) support comparing an arbitrary ticker's on-demand score against the real shortlist bar.
- **Portfolio value over time** — `data/portfolio_history.json` (`[{date, value}]`). `record_portfolio_snapshot()` upserts today's total (one point/day) on every Refresh-all and in `daily_check.py`. `POST /api/portfolio-history/seed` reconstructs an *approximate* backward curve from Alpha Vantage daily history of current holdings (current shares × past close × current FX; manual holdings flat) for dates not already recorded — approximate + AV-budget-limited, so it's an opt-in button. Line chart at the bottom of My Stocks (`renderPortfolioChart` in `app.js`). Below it, a **weekly value-by-stock table** (added 2026-08-15) reads the same total history plus a new `data/holdings_history.json` (`[{date, ticker, value}]`, `record_holdings_snapshot()` alongside `record_portfolio_snapshot()` at the same two call sites, `GET /api/holdings-history`). Per-stock tracking only started that day, so per-stock cells show `–` for older weeks while the Total column (longer history already) fills in fully. Table is **weeks-as-rows** (Mon–Sun date range, newest first) **× stock-as-columns + Total** — deliberately transposed from an earlier weeks-as-columns draft, since weeks grow unbounded over time and stocks don't (a "Show more weeks" button reveals older rows past the initial 10, `renderWeeklyTable`/`weeklyTableWeeksShown` in `app.js`). The colors/values themselves were still computed off the correct underlying week buckets, so this was a display-only bug, not a data bug. Fixed by building the date string from local `getFullYear`/`getMonth`/`getDate` instead of `toISOString()`.

Descriptive only (no "will outperform"). `data/sector_strength.json` + `data/ticker_sectors.json`. **Watch the shared Alpha Vantage 25/day cap** — sector build (11) competes with price charts + Analyze sentiment. Deferred data-source ideas live in `docs/plans/roadmap.md`.
- `zacks_import.py` — parses Zacks screen CSV exports (`data/zacks_ranks.json`). On re-import it refreshes each ticker's CSV metrics but **preserves the enrichment fields** (`PRESERVED_KEYS`: consensus/consensus_avg — filled by the separate ~4-min consensus batch, not the CSV, so a re-import mustn't wipe them), and **prunes tickers that dropped off** the list, scoped to only the rank tier(s) present in the imported file (Rank 1 churns ~35-40%/day, so both matter). Returns added_count/removed_count.
- `notifier.py` — Gmail SMTP for alert emails (`GMAIL_ADDRESS`/`GMAIL_APP_PASSWORD` in `.env`).

- Static frontend (`static/`) — five tabs: "My Stocks" (holdings, alerts, Sell), "Opportunities" (Zacks Rank 1 table, per-ticker Analyze, two-ticker Compare), "Opportunities B", "Watch List", and "History" (sales log, removable entries).
- **Watch List** (`data/watchlist.json`) — manually added/removed tickers you're considering but haven't bought; not a broker sync. Each item carries price, 1W/3M trailing returns, Opportunities-B score, and analyst consensus, all refreshable per-row or via Refresh all (`POST /api/watchlist/{id}/refresh` / `/refresh-all`, 1s spacing between tickers for Finnhub's rate limit). Same "Zacks / Cons." column and Analyze/Compare (`compareTickers('watch-compare-a','watch-compare-b')`) as My Stocks/Opportunities, reusing the shared `zacksCell()`/consensus-modal/compare-modal code — **`zacksCell()` takes the whole row object** (needs both `.ticker` and `.consensus_avg`), not a bare ticker string; passing the string silently produces all-dashes instead of an error, which is what broke this column until 2026-08-11. A first version split this into a separate `tag` column with autocomplete, and that was **rolled back the same day**: a tag only pays off if its wording stays consistent, the user maintains it by hand, and the sources vary — so grouping now comes from **#hashtags typed inside the why text** (`HASHTAG_RE`/`watchHashtags()` in `app.js`), which creates a new group just by typing one. Clickable chips above the table (`renderWatchTagFilters()`) show each hashtag with a count and filter the list. `source_url` is validated http(s)-only by `clean_source_url()` — it renders as a clickable link, so a `javascript:` URL would execute on click. **The entry snapshot (`price_at_add`/`score_at_add`/`consensus_at_add`) is captured automatically on add**, which drives the since-added % beside the Added date (hidden on the day the item was added, where it is 0,0% by definition and duplicates the 1D column — and computed from local date parts, never `toISOString()`, which is the UTC bug that shifted the weekly table's dates); rows added before this existed show `–` rather than a backfilled guess (reconstructing entry prices from Alpha Vantage costs budget and is only approximate). `load_watchlist()` runs a one-time idempotent migration keyed on a missing `why` or a leftover `tag`, folding the older `note` and `tag` into `why`. Client-side sortable by ticker/score/1W/3M/momentum (`watchSortBy()`), same click-toggle-arrow pattern as the Opportunities tabs. The **Momentum** column (2026-09-04) comes from `momentum.from_finnhub()` and is free — `fetch_watch_data()` now makes a single `prices.fetch_quote_shape()` call (raw USD o/h/l/c, replacing the old `fetch_quote`) plus one `prices.fetch_metrics()` whose raw dict serves both the 1W/3M returns and the momentum read, so the column added no API calls and actually removed a duplicate `/quote`. A row that has never been refreshed shows `—`; a refreshed row with nothing happening shows `quiet` — deliberately different strings, since a bare dash for both made a working scan look broken.

- **Refresh skips the price fetch entirely on weekends** (`prices.is_weekend()`, both `refresh_holding_price` and `refresh_all_prices` in `main.py`). Real incident (2026-08-15): ls-tc.de still returns "intraday" ticks on a Saturday/Sunday with a stale `previousDay` reference — a fabricated non-zero `day_change_pct` for some tickers, an exact-zero for others, neither a real weekend price move. Since no exchange is open at all on a weekend, there's nothing real to fetch from *any* source, not just L&S — so the guard skips price/`day_change_pct` entirely (left exactly as last set) rather than trying a fallback. Analyst consensus still refreshes, since that's not tied to market hours.

## Reviewing the copy

`node tools/copy_review.js` — free, reads stored data, calls nothing. Two parts:

- **Per-ticker snapshot + invariance check.** Prints each ticker's rendered copy and flags any
  line byte-identical across all of them. Per-item text that never varies is not about the
  item — the exact fault behind "Your holdings already include one bloc…" and "is the stock
  swimming with or against its sector's tide?", both of which read as facts about the stock.
- **A synthetic case matrix for the badge copy.** Every branch of `renderFundamentals` side by
  side from made-up inputs. This is where the value is: it caught a live bug on its first run
  (the "both falling" branch said "while profits grew" when profits had fallen 15%) that no
  current ticker would have exposed. Clicking through real data only tests the cases you
  happen to hold.

**This is not an eval, and the distinction matters.** Evals are for output you cannot predict.
Nearly all the text in this tool is written in `app.js` and `synthesis.py`'s deterministic
`derive_signals()` — same input, same output — so a snapshot plus a few assertions covers it at
a fraction of the cost. Only `synthesis.py`'s LLM prose is generated, and that is the one
surface where evals would earn their keep; the script deliberately does not touch it. A useful
test for which is which: if you can `grep` the exact sentence in the source, a human wrote it.

## Gotchas

- **`data/` is backed up daily by `backup_data.py`** (launchd `com.tradingtool.databackup`, 07:30, `RunAtLoad`) to `~/Documents/trading-tool-backups/<YYYY-MM-DD>/`, keeping the newest 30 daily snapshots (~750 KB each). This exists because git no longer holds a copy (see the next bullet) — and the irreplaceable parts can't be rebuilt from anywhere: `portfolio_history.json` and `holdings_history.json` are time series only recordable going *forward*, `holdings.json` carries `reference_high`/`trailing_pct`/`exit_plan` that the broker doesn't know, and `watchlist.json` holds the free-text notes. Restore = copy the files back into `data/`. It's Python run through the venv interpreter rather than a shell script specifically because that binary already has Full Disk Access (see the launchd gotcha below); a bash script would hit the same silent `PermissionError`. Log: `backup_data.log`.
- **`data/` is not tracked by git and must stay that way** (2026-09-04). Real holdings, watchlist, sales and portfolio-value history, and the API caches (`ls_tc_cache.json` included — its ISIN keys reveal positions) are all gitignored. Only `holdings.example.json` (schema sample) and `sp500.json` (bundled reference data Opportunities B needs) are committed. These files *were* previously committed; the history was rewritten with `git filter-repo` and force-pushed to purge them, and real share counts/sale totals/trade figures in CLAUDE.md, README.md and the roadmap were replaced with illustrative ones at the same time. The repo has always been private, so nothing was exposed — the point was to unblock ever making it public, since the user showcases projects to recruiters. Tickers still appear in docs as engineering case studies (deliberate); actual figures do not. `load_holdings()` returns `[]` when the file is absent so a fresh clone starts empty instead of crashing. **Don't `git add` anything under `data/`, and don't put real position numbers in tracked docs.**

- Scripts invoked via `launchd` need **Full Disk Access** granted (System Settings → Privacy & Security) to the actual Python binary the venv symlinks to (not the symlink) — otherwise silent `PermissionError` reading `~/Documents`/`~/Downloads`.
- The Browser-pane preview proxy can serve a stale cached page; append `?cb=<anything>` to force a fresh load when verifying UI changes.
- **Static files are served with `Cache-Control: no-cache`** (`RevalidatingStaticFiles` in `main.py`) so the browser revalidates `app.js` on every load. Chrome was caching it heuristically and silently running an old copy after an edit — on 2026-09-05 that had the user reporting a bug twice that had already been fixed, because her browser never picked up the new script. `no-cache` still caches; it just checks the ETag each time, so an unchanged file returns 304 and costs nothing. Right for a local single-user tool, wrong as a public-site default. If a UI change still doesn't appear, the server itself needs the launchd restart (launchd runs without `--reload`).
- **Anthropic API calls**: always pass `thinking={"type": "disabled"}` unless you actually want extended thinking — Sonnet 5 defaults to *adaptive* thinking when unset, which can silently consume the whole `max_tokens` budget and return a `['thinking']`-only response with zero actual text. Never index `message.content[0]` directly; filter for `block.type == "text"` instead, since block order/composition isn't guaranteed.
- `render()` in `app.js` is async — always `await` it before code that depends on the DOM being updated, or you get race conditions (happened once with price colors).
- **All numbers shown to the user are EU-formatted** (period thousands, comma decimal — `1.234,57`). The web UI does this via `Intl.NumberFormat("de-DE")` (`fmt`/`fmtPct` in `app.js`); the daily email does it via `eu_num`/`eu_pct` in `daily_check.py` (Python has no clean locale-free equivalent, so those use a format-then-swap trick). Any new user-facing number — web or email — must go through one of these, never a raw `:.2f` / bare float.
- **EU number entry**: every numeric field the user *types* uses `type="text"` + `inputmode="decimal"` and is parsed with `parseEuNumber` (never `<input type="number">`, which silently drops the comma — typing `1.234,56` becomes `1.23456`). This trap caused three real data-corruption incidents before it was fully closed: two sale totals, and a fractional share count (`1.234,567890` → `1.234567890`, 1000× too small, which also threw off the portfolio total). Hardened fields: Add form, Edit form (shares/cost/stop/trailing-high/price), and both sell inputs. `parseEuNumber` handles EU `2.345,67`, US `2,345.67`, no-grouping `2345,67`, and the malformed-but-common all-one-separator forms `2,345,67` / `2.345.67` (last separator = decimal, rest = grouping; a same-separator string ending in a full 3-digit group like `1.234.567` is treated as pure grouping). Edit/sell fields are **pre-filled** via `toEuInput` (comma decimal, no grouping) so the displayed value round-trips cleanly back through `parseEuNumber` — don't pre-fill a raw JS number string into these, since e.g. `1.234` would be misread as EU-thousands `1234`. Read-only share counts display via `fmtShares` (grouped, up to 8 decimals). Backstop for sales: the sell endpoint rejects a per-share price >10× off `current_price` (`SALE_PRICE_SANITY_FACTOR`) with a confirmable `price_sanity` 422.

## Hard rules (established through real back-and-forth, don't relitigate)

- **No directive financial advice, ever, in any feature.** Alerts/analysis surface facts (gain/loss, tax estimate, consensus, momentum) and let the user decide — never "buy X" / "sell now" / "this is the best pick." This applies even to LLM-generated prose synthesis features: explaining what data shows is fine, concluding what to do with it is not.
- **No automated login/scraping against a service's ToS**, even for the user's own paid account (Zacks Premium, Yahoo Finance's unofficial endpoints). CSV export + manual/automated *ingestion* of that export is fine; automating the *acquisition* via login is not.
- **Test API endpoints live before committing to a plan.** Docs can be wrong or describe a paid-only tier (Finnhub's news-sentiment and price-target endpoints looked promising in docs, both 403'd on the free tier in practice). Another live-tested example (2026-08-17): Finnhub's `calendar/earnings` **cannot** retrieve historical earnings report dates on the free tier — with a `symbol` filter it only ever returns *future* events regardless of the date range asked for; without a symbol filter it returns real historical data, but capped at ~1,500 rows per call, and during earnings season that's consumed by ~10-14 days of the whole market reporting, so anything further back is simply unreachable no matter how the date range is set. This blocks building a per-ticker multi-quarter "did the price react to the beat" history from Finnhub alone. The pivot to Alpha Vantage's `EARNINGS` endpoint worked (live-verified 2026-08-18, real `reportedDate` per quarter, e.g. MU: 122 quarters back) but the feature was still dropped — no free source for the years of price history the reaction check needs: Alpha Vantage's `outputsize=full` on `TIME_SERIES_DAILY` is premium-only, and Stooq (considered as a free no-key alternative) disallows automated access via `robots.txt` (`Disallow: /` except for search-engine crawlers) and its CSV endpoint now sits behind an active bot challenge. See `docs/plans/roadmap.md` for the full trail.
- Prices are always **EUR** — Trade Republic quotes everything in EUR even for US-listed stocks. Any new price data source must convert or fetch EU-listing prices, never assume USD.
- **Finnhub free tier is US instruments only** — non-US ordinary shares and `.HK`/`.F`/`.DE` listings 403. So a Trade Republic holding whose real instrument is EU/Asia-listed, or a US ADR with a share-ratio mismatch (LNVGY = 20 Lenovo ordinaries → ~20× the TR price), can't be auto-priced from Finnhub's absolute number. **First option now: add its ISIN** (see `ls_tc.py` above) — L&S prices the real underlying instrument directly, sidestepping the ratio/wrong-instrument problem entirely rather than working around it. This is exactly how LNVGY was fixed (2026-08-13): its ISIN is the actual HK-listed Lenovo Group ordinary, not the ADR, so `manual_price` was turned off once the ISIN was added. Only fall back to `manual_price: true` if no ISIN gets a hit on L&S either. For holdings still on `manual_price: true`, their absolute Finnhub-fetched price is never usable — `refresh`/`refresh-all`/`daily_check` never adopt it directly — but if the ticker is still fetchable at all, its `day_change_pct` still is and gets rolled in the same way as any other holding (see the price-rollforward rule below). If the ticker can't be fetched at all, the price just stays frozen for that refresh. For non-manual, non-ISIN holdings, refresh still detects a gross mismatch via `is_price_mismatch` (fetched >`PRICE_MISMATCH_FACTOR`× off stored `current_price`) and returns a `price_mismatch` payload instead of clobbering; the frontend turns that into a "keep mine (manual) / use fetched" prompt.
- **Holding prices roll forward by relative % change, not absolute overwrite — and only while the US market is open.** `apply_quote()` (`main.py`) doesn't replace `current_price` with Finnhub's raw converted price on refresh — Finnhub's absolute number never matches Trade Republic's real price exactly (TR trades US stocks via Lang & Schwarz, not Nasdaq directly, plus a different FX conversion), so overwriting outright re-imports that gap every time. Instead it keeps an anchor per holding (`price_anchor`, `anchor_fx_rate`, `anchor_previous_close_usd`) — your last TR-verified price — and rolls it forward by Finnhub's `day_change_pct` and by how much USD/EUR moved since the anchor was set. The anchor only advances when Finnhub's own previous-close reference changes (a new trading day); applying `day_change_pct` again on an already-rolled price would double-count the same move on a second same-day refresh. **This roll only runs while `prices.us_market_open()` is true (9:30–16:00 ET, Mon–Fri, holidays not accounted for)** — while the US market's closed, Finnhub is frozen on the last close, so `day_change_pct` is a move that's already fully realized and likely already reflected in a TR-verified anchor; applying it anyway double-counts it. Real incident that surfaced this (2026-08-11): DK showed 54,49 in the tool vs 52,38 on TR while TR was actively trading and the US market was shut. `day_change_pct` itself still updates unconditionally either way (it drives the Today % badge regardless of market hours). Editing `current_price` directly (`PUT /api/holdings/{id}`, the Edit form) invalidates the anchor, so the next refresh re-bootstraps it — but a missing anchor means two different things, and they need different math: a genuine new trading day (anchor present but its `anchor_previous_close_usd` is stale) means the stored price is a valid prior-close baseline, so today's full move applies to it as-is; a same-day manual edit (or a brand-new holding) means the stored price already reflects "right now," so naively treating it as the baseline and applying `day_change_pct` on top double-counts whatever move had already happened by edit time. Real incident (2026-08-11): after manually syncing every holding to TR one by one that morning, every single one drifted again within the hour — some over, some under, depending on which way that ticker was moving at edit time — because the bootstrap didn't distinguish the two cases. Fixed by backing out the equivalent close-basis anchor (`current_price / (1 + day_change_pct)`) only in the missing-anchor-this-session case, so that refresh reproduces the price you just entered instead of jumping.
- **Today % is the only price-direction color in the Holdings table.** An earlier attempt also colored Current price by refresh-to-refresh movement, alongside Today %'s day-over-day movement — having two differently-scoped color signals side by side just read as contradictory/confusing in practice, even though each was individually correct. Current price is now plain text; don't re-add coloring to it without a real reason. Same principle applies to the per-holding "no change needed" note under the table (`renderFlag`'s non-triggered branch, `main.py`'s `evaluate_trailing`) — it's plain `--text` colored, not green/red, since it's non-actionable and shouldn't compete visually with real alerts (stop-hit, breakout).
- **Manual trailing-stop reset, stop-hit alert only** (2026-08-15) — `evaluate_trailing()` (`main.py`) always computes `reset_new_stop` (current price × (1 − `trailing_pct`)), not just when `triggered`. The **stop-hit** panel (`renderFlag`'s `stop_hit` branch) shows a "Reset trailing stop to current price" button (`resetTrailingStop()` → the existing `confirm_trailing_stop` endpoint), setting `reference_high` to the current price and recomputing `stop_price` from the same `trailing_pct` — for when you consciously decide to hold through a breach instead of selling. Guarded by `window.confirm()` since it silently changes a real protective level. **Deliberately not on the passive "no change needed" message** — a first version put it there too and Liraz found it cluttered a status that's supposed to be plain and non-actionable (same reasoning as the color-restraint rule above); rolled back to plain text there. Real incident that motivated this (2026-08-15): NBIS's `reference_high` had been frozen since before an actual stop-loss breach Liraz chose to hold through, so the trailing high never advanced — the stop sat ~30% below the current price (mathematically correct for its wide 22.9% `trailing_pct`, but functionally stale) with no way to re-anchor before this button existed.
- The client-side **"US market closed" banner was removed** (2026-08-15) — `usMarketOpen()`/`updateMarketStatus()` in `app.js` and `#market-status` in `index.html` are gone. With every current holding ISIN-priced via L&S (live ~07:30–23:00 CET, independent of US market hours), the banner was stale every time it showed. **This is separate from `prices.us_market_open()`** (Python, still used by `apply_quote()`'s Finnhub anchor-rollforward gate — see the price-rollforward rule below), which stays since it's still correct for the Finnhub fallback path. If a future holding has no ISIN (or L&S fails outside its hours), there's currently no on-screen hint its price might be stale — fine for now since no current holding hits that path, worth revisiting if one does.
- `daily_check.py`'s FX-rate fetch and email send each retry up to 3x (~20s apart) — a real missed-alert incident happened when a launchd-fired run right after sleep/wake hit a DNS failure because Wi-Fi hadn't reconnected yet, and the fallback "check failed" email failed for the identical reason, so the failure was completely silent. Don't remove the retry without addressing that failure mode some other way.
- **Today % comes from Finnhub's own `dp` field (`/quote`), not a self-tracked "day open" snapshot.** A first version tried storing "the first price we saw today" and comparing against that — but that first refresh can happen well after a big intraday move already occurred (e.g. testing mid-session), producing the exact same wrong-direction bug one level up. Finnhub already computes the change vs. its real previous close server-side, in the same `/quote` call we already make for the price — use that directly, don't re-derive it.
- When adding a new "check something and alert" trigger, keep the persistence pattern already used for price/consensus coloring: only overwrite the "previous" value when the new value actually differs, so a no-change refresh doesn't erase the last real signal.
